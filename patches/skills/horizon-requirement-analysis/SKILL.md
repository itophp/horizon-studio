# Horizon 需求分析与 AI 嵌入评估

Horizon 的 AI-Native 不是给页面加一个聊天框，而是让智能参与成为运行机制：**能力产生事实 → 事件驱动 AI → AI 只能通过能力写回 → 写回受来源限制**。因此每个功能都要先回答“AI 在这个业务里究竟做什么”，再决定能力、流程与代码。

产出不是一段说明，而是一份可审查的记录：业务步骤到 AI 角色的映射、责任边界、失败语义和验收用例。结论可以是「不需要 AI」，但必须有理由。

## 1. 还原业务过程

先把业务说清楚，再谈 AI：

- **入口**：页面按钮/表单、外部 API、Agent/MCP、事件/Trigger、定时任务、人工任务。
- **角色与范围**：谁创建、查看、修改、审核、被通知；能否自审；跨租户/跨部门如何隔离。
- **对象与状态**：涉及哪些实体和字段，动作前后状态，版本/并发条件。
- **成功与失败**：成功是什么状态；失败、取消、超时、撤回分别落到哪里。
- **人工等待与恢复**：谁批、批哪一版对象、理由必填吗、超时如何处理、重启后如何继续。
- **区分四种“完成”**：请求已受理、AI 判断完成、人工批准、业务已完成；不能互相替代。

## 2. 判断 AI 是否嵌入、嵌入在哪

逐条回答，答案要落到具体步骤：

1. 功能里哪一步需要**判断、生成、调查或复核**？如果没有任何一步需要，结论就是「不需要 AI」，不要硬加。
2. AI 的输出**被谁消费**？页面展示、流程分支、能力参数、通知还是人工决策材料。没有消费方的摘要/润色不算嵌入。
3. 这个输出**错了谁承担**？决定它应该只是建议、必须人工确认，还是绝不能自动推进。
4. 有没有**确定性规则可以替代**？能用权限、状态机、词表、阈值解决的，不交给模型。
5. **输入材料**来自哪里、是否已授权给当前身份？正文、凭证、敏感字段是否必须排除。
6. 是否需要**多轮调查与工具选择**？不需要就不要用 ADK，避免把一次分类包装成 Agent。

真正的嵌入通常同时具备：明确的业务步骤、结构化输出契约、确定性校验、人工责任边界、失败与降级路径、可复现的验收用例。

## 3. 划清责任边界

| 职责 | 归属 | 说明 |
|---|---|---|
| 身份、权限、租户与数据范围 | 确定性 | Gateway 与 SQL 执行，不由模型判断 |
| 状态机、版本与并发 | 确定性 | 条件更新，旧版本/旧结论不能覆盖新内容 |
| 金额、合规词表、配额、阈值 | 确定性优先 | 命中即拒绝或转人工，模型不能推翻 |
| 分类、生成、调查、复核 | 模型 | 必须结构化输出并校验 |
| 发布、高风险写入、争议裁决 | 人 | 审批/四眼；模型只能提议 |
| 模型结论归一化 | 确定性 | 例如原因码 → 单一 decision，再决定分支 |

AI 判断、风险确认与业务人工审核是三个环节：风险确认是 Gateway 对高风险动作的确认；业务审核包含审核人、任务范围、对象版本、通过/驳回原因与独立入口。不要用前者冒充后者，也不要用模型结论替代人工决定。

## 4. 选对形态

| 需要什么 | 形态 |
|---|---|
| 固定输入的单次分类、提取、生成 | 直接模型调用 + 结构化输出校验 |
| 需要调查、多轮读取受限工具并决策 | ADK Runner / ADK 节点，固定版本工具白名单 ∩ 当前权限 |
| 有界复核、轮询、只读重试 | Graph 子图，明确退出条件与步数上限 |
| 多步骤业务流程、等待人工、跨请求恢复 | Workflow 主干，AI 作为节点 |
| 由业务事件持续触发 | Outbox → Event Hub → Trigger（去重 + maxDepth），结果经能力写回 |

简单功能不强行包装成流程；需要业务流程时不要塞进一个能力或 Go 顺序调用。选型细节见 `horizon-workflow` Skill。

## 5. 输入与权限边界

- 只放行当前身份已授权的字段投影；正文、凭证、内部备注等敏感内容默认不进模型，确需使用时在记录里逐项说明。
- 知识、历史记录与记忆要注明来源、范围与时效；记忆不能授予执行权限。
- Agent 工具只给固定版本允许列表与当前权限的交集，不因任务需要临时扩大。
- 审计只记录必要字段与摘要，不把模型原文中的敏感信息写入日志或检查点。

## 6. 先定失败与降级

| 情况 | 业务行为 |
|---|---|
| 模型不可用、超时、限流 | AI 任务记失败；业务对象保持原状态；可重试或转人工，不阻塞无关流程 |
| 结构化输出缺字段、未知取值、版本不符 | 判为 `invalid`，不落库、不推进分支；允许一次只重述结论的纠正追问，仍失败则失败 |
| 结果不确定或低置信 | 保持待审或转人工，不自动通过 |
| 输入含未授权或敏感材料 | 拒绝发给模型，缩小投影或改人工处理 |
| 重复事件、重试、恢复 | 同一逻辑动作复用幂等键，事件去重，不重复生成或重复写回 |
| 人工驳回或撤权 | 流程终止或回到可修改状态；模型不能自批或自动重试绕过 |

AI 失败不等于业务失败；业务成功也不能掩盖 AI 失败。缺少结果或不确定时不得当作通过。

## 7. AI 写回

- 写回是独立能力，经 Gateway 执行；按场景只接受 `OriginAgent` / `OriginWorkflow`，拒绝人工或外部 API 直接伪造“AI 结论”。
- 条件更新要同时校验对象状态、版本与结论码；确定性规则（如命中的词表）优先于模型结论。
- 只落归一化后的事实（原因码、decision、摘要），不把模型散文当作业务事实。
- 人工闸门放在 Gateway 策略里，不写在提示词里；模型不能批准自己的动作。

## 8. 验收用例

至少覆盖：正常路径、模型输出非法/缺字段、模型不可用、越权或敏感输入被拒、重复事件不重复写回、人工驳回后旧结论不推进、跨租户访问、无关流程不受影响。

用 stub 替换整条 AI 路径只能证明路由，不能证明接入；至少用真实引擎和可控模型验证，并说明哪些在线模型/客户端行为尚未验证。

## 9. 记录模板

| 列 | 内容 |
|---|---|
| 业务步骤 | 动作、对象、前后状态 |
| AI 角色 | 判断/生成/调查/复核；无 AI 时写明理由 |
| 输入与敏感边界 | 来源、字段投影、绝不能进模型的内容 |
| 输出契约 | 结构化 Schema、允许取值、版本 |
| 确定性校验 | 规则、状态、版本、字段权限 |
| 人工闸门 | 谁批、批哪一版、意见与超时 |
| 失败与降级 | 每种失败的状态与去向 |
| 引擎 | 单次模型 / ADK / Graph / Workflow / Trigger |
| 验收用例 | 成功、拒绝、失败、重放、越权、人工介入 |

最小架构记录可写为：`目标能力@版本 → 复用/新增结论 → AI 嵌入点与形态 → 输出契约与校验 → 人工与失败边界 → Plan/Binding（未切换则注明）→ 验证与回滚证据`。

## 10. 反模式

- 为“AI 原生”而加模型：没有消费方的摘要、润色、标签。
- 让模型决定分支或直接改状态；分支不读落库后的归一化事实。
- 模型直接写库或绕过 Gateway；用一次模型调用冒充 Agent 接入。
- 结构化输出缺失或未校验，把散文当契约。
- 把 AI 建议当人工审批，或把风险确认当业务审核。
- 没有失败路径，把超时、缺字段、低置信当成功。
- 输入未做敏感与授权评估，把正文或凭证发给模型。
- 为复用而把多步骤业务流程塞进一个能力。

## 11. 边界

Horizon 是 AI-Native 框架，但这不意味着每个功能都必须使用 AI。评估的合法结论包括「这一步用确定性规则更可靠」「这里不需要模型」「当前风险下先交人工」。不要为了满足流程而硬塞模型、扩大权限或增加无消费者的 AI 输出。
